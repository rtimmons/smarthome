# Private LAN access to the cloud interfaces

The private LAN connection is live as of September 11, 2026. Tunnel negotiation,
rekeying, automatic recovery, anonymous denial, and user logins to both SABnzbd
and Prowlarr have passed.

The USG 3P maintains a policy-based IPsec connection to the existing Hetzner VM.
Home clients need no VPN application or workstation SSH tunnel. The cloud
applications keep their existing loopback-only bindings; an authenticated proxy
provides the private endpoints:

| Interface | Private address |
| --- | --- |
| SABnzbd downloads | `http://10.77.0.1:18080/` |
| Prowlarr search | `http://10.77.0.1:19696/` |
| QNAP catalog/cache | `http://192.168.1.66:1337/` |

At the browser's authentication popup, use the existing catalog dashboard
username and password for either cloud address. Prowlarr then shows its own
login page, which uses the existing Prowlarr account. These are separate logins;
the new access path does not change either password. Home Assistant may link to these pages
or show SABnzbd status; it does not carry the VPN connection. QNAP handles the
catalog and local cache.

## Scope and compatibility

Verified on September 10, 2026: Cloud Key Gen2 Plus, UniFi OS 5.1.31, Network
10.6.101, USG 3P firmware 4.4.57.5578372; cloud Ubuntu 26.04.

The intended scope is only the Default LAN (`192.168.1.0/24`), excluding the
printer network (`192.168.6.0/24`) and existing remote site (`192.168.8.0/24`).
The legacy gateway requires the provisioning override below to enforce that
scope; the modern controller form alone did not do so.
The controller rejects a `/32` remote subnet, so the VPN selectors use the
dedicated `10.77.0.0/30` subnet. Only `10.77.0.1` is assigned, and the cloud policy
permits only TCP 18080 and 19696 to it. Other addresses/forwarding are denied.
Normal Internet traffic, acquisition traffic, and the existing site VPN retain
their current configuration.

The supported USG form offers IKEv2, AES-256, SHA1/MD5, DH14, and PFS. This
connection deliberately uses SHA-1 **only as HMAC in IKE/ESP**, with AES-256,
DH14, PFS, a random 256-bit pre-shared key, and no algorithm fallbacks.
strongSwan documents this compatibility option for systems lacking SHA-256.
It is a legacy constraint, not equivalent to a modern SHA-256 configuration;
migrate when the gateway is replaced. Never substitute MD5, 3DES, or IKEv1
aggressive mode. [strongSwan security guidance](https://docs.strongswan.org/docs/latest/howtos/securityRecommendations.html)

IPsec encrypts traffic between the gateway and cloud VM. These HTTP endpoints
do not add browser-to-gateway TLS on the LAN. No public web ports are opened.
UDP 500/4500 are restricted to the verified home WAN address in both Hetzner's
firewall and UFW. Host policy also requires the matching IPsec peer and blocks
plaintext fallback. Exact same-address loopback health probes are permitted.

## Deployment and recovery

`just usenet-configure-cloud-lan-ui` installs only the new VPN and proxy. Their
roles are also included in a full cloud rebuild when `cloud_lan_ui_enabled` is
explicitly enabled in the ignored deployment inventory. The root-owned
configuration lives under `/etc/usenet-vpn` and `/etc/usenet-cloud-ui`; root-run
helpers live under `/usr/local/libexec/usenet-vpn`.

Ubuntu's enforced `swanctl` AppArmor profile initially denied access to the
custom private configuration. The role adds only
`/etc/usenet-vpn/swanctl.conf r,` to its local profile include and reloads the
profile, retaining root-only file permissions and AppArmor enforcement. The
loader requires fresh connection and credential acknowledgments, then verifies
the exact running IKEv2 connection and tunnel child. An empty configuration can
otherwise make `swanctl --load-all` exit successfully; it now fails deployment
and service startup. The check uses the installed version's supported
`--list-conns` command and selects the connection locally.

### Legacy USG provisioning override

On September 11, the saved Network 10.6.101 form specified IKEv2 and only the
Default LAN, but the USG's generated configuration used IKEv1 and included a
second tunnel for the printer VLAN. Actual LAN-triggered negotiation confirmed
IKEv1. Saved UI values are therefore insufficient evidence of deployment.

The reviewed repository file `usenet-infra/unifi/config.gateway.json` adds
dedicated `USENET_UI_IKE` and `USENET_UI_ESP` groups for the new peer
`89.167.18.138`. It specifies IKEv2, AES-256/SHA-1, DH14/PFS, sets tunnel 0 to
`192.168.1.0/24` ↔ `10.77.0.0/30`, and disables autogenerated printer tunnel 1.
Existing groups, the other site VPN, and credentials are preserved. After any
LAN/VLAN topology change, recheck generated tunnel numbers and disable any new
out-of-scope tunnels; the cloud selectors and firewall independently deny those
subnets.

For recovery, review and copy this file to
`/data/unifi/data/sites/default/config.gateway.json` on the Cloud Key, owned by
`unifi:unifi` with mode `0644`, and reprovision through UniFi. Create missing
site directories with the same owner. `/usr/lib/unifi/data` resolves to that
active data root; `/srv/unifi/data` is an older, separate directory on this
console. Preserve and merge any future override content before copying. Do not
reboot the gateway or edit its generated `config.boot` directly. Verify the
resulting gateway configuration and policies after provisioning, including the
absence of an active printer tunnel. On the initial installation here, the
UniFi Network service was restarted to pick up the override, followed by a
controller save/reprovision. The gateway and NAS were not rebooted.

Keep the pre-shared key in the ignored mode-0600 file
`secrets/unifi-cloud-vpn.psk`; enter it privately into the prepared UniFi form.
Do not paste credentials into chat, source files, diagnostics, or screenshots.
The UI requires a human to enter and submit the new credential.

Before deployment, a fresh encrypted cloud backup and both UniFi Network and
full System backups were verified. Their archive paths and evidence are recorded
in `plan.md` and the ignored `build/unifi-*-backup-*.json` files. Backup encryption
uses the existing dedicated cloud-administrator key; no 1Password private key
is exported. New root-owned VPN/proxy settings require their separate encrypted
VPN backup in addition to ordinary cloud application backups.

If the home WAN IP changes, review and update both VPN endpoint identities and
the peer restrictions in Terraform, UFW, and UniFi. Do not widen the source to
all Internet addresses. If rollback is necessary, stop the new proxy and VPN
services first, remove only `usenet-cloud-ui` in UniFi, and remove only the new
Terraform VPN ingress rules. Remove only this peer's override keys and the
dedicated `USENET_UI_IKE`/`USENET_UI_ESP` groups, preserving any other content in
`config.gateway.json`, then reprovision through UniFi. Preserve the existing site VPN, SSH, cloud
applications, storage, and QNAP services. Keep the private-address deny policy
until the private listener and address have been removed.

Acceptance must verify LAN login, anonymous denial, actual selectors and peer,
an explicit CHILD-SA rekey, reconnection, unchanged application health/default
routes, blocked unrelated ports, and a verified post-change encrypted backup.
Never print raw `ip xfrm state`: it can expose session encryption keys.

September 11 evidence: the gateway provisions only the intended new LAN tunnel
with IKEv2, AES-256/HMAC-SHA1 and DH14; an explicit CHILD-SA rekey verified PFS14.
Restarting strongSwan on the cloud host automatically re-established the tunnel
and private proxy. LAN requests to both private ports returned HTTP 401 without
credentials, and direct backend ports 8080/9696 timed out. The existing site VPN
configuration and workstation default route were preserved. Repeat cloud
deployment reported zero changes. Encrypted, authenticated-decryption-verified
post-change backup includes the actual gateway configuration, saved UniFi VPN
record, and installed override; see `plan.md` for its path and checksum.
