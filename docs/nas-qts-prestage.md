## Local accounts

Use [QTS local user creation](https://docs.qnap.com/operating-system/qts/5.2.x/en-us/creating-a-local-user-A3835C8C.html)
under Control Panel → Privilege → Users → Create a User. Use the autogenerated
UID, only the required `everyone` group, no email notification, and no SSH,
application, network-service or share grants. Existing `Public` allows
`everyone` to read, so explicitly deny **Public** for each new account, with
**Apply changes to subfolders** off. Deny any other inherited share access
found during readback. Disable the newly created account in its QTS profile
until the activation checkpoint; verify it still resolves to its assigned UID.
The operator enters and submits each initial password in QTS; do not create a
plaintext import or record credentials in evidence. [QTS's CSV format](https://docs.qnap.com/operating-system/qts/5.2.x/en-us/creating-a-csv-user-file-933E102C.html) cannot
set the per-account application privileges and share denials in this checklist.

## Empty shares

Use Control Panel → Privilege → Shared Folders → Create → Shared Folder.
For each share, choose **Specify path automatically**. Clear the default
explicit read/write grant for the signed-in administrator; keep the standard
QTS administrators recovery access. Give no direct read/write grants, deny
guests, require SMB encryption, enable ABE and ABSE, and leave recycle bin and
Time Machine off. Keep the other wizard defaults; SMB transport encryption
does not create a folder-encryption key. Mark the share empty pending cutover.

| QTS volume | Backing parent | Shares |
| --- | --- | --- |
| Scratch | `/share/CACHEDEV1_DATA` | `jellyfin`, `media-control`, `filex`, `dns`, `remote-reader`, `remote-maintainer`, `hetzner-gateway`, `backup-control` |
| GPvQNAP | `/share/CACHEDEV2_DATA` | `forgejo-backups`, `infrastructure-backups`, `HomeAssistantBackups`, `MediaCache`, `PlaybackCache`, `TransferStaging` |

Leave `Documents` for household classification, and preserve personal homes.
The remote views `RemoteMedia`, `RemoteManage`, `RemoteFiles` and `Hetzner`
need a real mount, startup guards and an access policy; an empty local share
would present the wrong data source. Leave those views, existing shares and
the Scratch label untouched.

## Acceptance and next cutover

1. Before saving the batch, recheck account and share absence in QTS and retain
   a private native QTS settings export. If a name already exists or points
   to a directory, stop that item and reconcile it rather than overwriting it.
2. After saving, verify each new account's UID, group, disabled status and
   denied QTS privileges, including the account-specific `Public` denial.
   Verify each SMB share's real path and saved permissions, including that
   there are no ordinary user, group, or guest grants. Confirm existing
   accounts and share mappings are unchanged.
3. Inspect the empty root and its ACLs separately from SMB settings. QTS
   previously created service roots at mode 0777 with inherited ACLs. Keep
   these roots empty until each cutover qualifies host permissions, current
   clients, deployment paths, backup coverage and rollback. Export and escrow
   current native QTS settings after the batch; verify the export date and
   include it in a later qualified recovery capture.
4. Reconcile the private UID and share mapping receipt before choosing the
   first activation. Start with the scanner-only checkpoint when ready; its
   configuration and state bind ACLs, UID switch, health, and rollback remain
   explicitly scoped in the [migration plan](plan-nas-storage-and-access.md).
